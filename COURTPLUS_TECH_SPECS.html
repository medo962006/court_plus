1 System Architecture Overview

Court+ follows a layered Clean / Feature-First architecture in Flutter. The codebase is organised into three primary layers: Presentation (screens, widgets, providers), Domain/State (Riverpod providers, notifiers, state classes), and Data/Repository (Supabase service, models, RPC wrappers). Each feature domain (auth, booking, social, profile) owns its slice across all three layers.

2 Frontend Specifications (Flutter)

NAV Routing & Navigation

Centralised route table in lib/routes.dart using named routes with MaterialPageRoute and custom slide/fade transitions. All screen routes are defined with static constants (Routes.courtDetails, Routes.notifications).

STATE State Management

Riverpod 2.x with StateNotifierProvider for complex state (auth, booking, social) and Provider for singletons (Supabase service). Async data fetching uses FutureProvider/StreamProvider with .when() builder pattern.

L10N Localisation

AppStrings class in lib/l10n/ with 220+ keys. Bilingual (English/Arabic) with runtime language switching stored in SharedPreferences. All screens wired to AppStrings.of(context).t('key').

THEME Design System

Light theme defined in lib/theme/app_theme.dart. Custom AppColors palette (neonGreen, lightText, lightMuted, lightBg, lightBorder). Consistent 14px input radius, 12px card radius, 16px default padding.

WIDGETS Reusable Components

Custom widget library: ShimmerWidget, CourtCardSkeleton, ShimmerList (skeleton loading), BouncingButton (spring scale + haptic), AnimatedCount (TweenAnimationBuilder), CheckmarkAnimation (elastic bounce), FloatingEmptyState (bobbing float).

MEDIA Image Service

ImageService in lib/services/ handles local picking via image_picker, caching, and upload to Supabase Storage bucket. Used by the profile avatar upload flow. Image paths are stored in the profiles.avatar_url column.

3 Backend & Database Specifications

Auth & Session Flow

Authentication is handled by Supabase Auth (gotrue). The app supports email/password signup with full metadata (gender, DOB, phone/dial code), email OTP verification, password reset, and guest/anonymous mode. Session persistence is automatic via supabase_flutter token refresh. A database trigger (on_auth_user_created) automatically creates a profiles row on user registration, copying raw_user_meta_data into profile columns.

Concurrency & Slot-Locking RPC Engine

The slot-locking engine is the core transactional feature. It uses PostgreSQL RPC functions to ensure atomic lock acquisition and release, preventing double-booking at the database level.

1

User selects a date

SupabaseService.getAvailableSlots(courtId, date) → calls get_available_slots(court_id, date) RPC

Returns list of CourtSlot objects with isAvailable and isLocked booleans. Locked slots owned by other users are grayed out; locked slots owned by the current user show as reserved.

2

User taps an available slot

SupabaseService.lockBookingSlot(courtId, slotId, userId) → calls lock_booking_slot(p_court_id, p_slot_id, p_user_id) RPC

On success: { success: true, locked_until: timestamp }. The RPC sets court_slots.is_locked = true, locked_by = user_id, locked_until = now() + 15 minutes.

On failure: RPC returns { success: false } if the slot was already locked by another user in the transaction window. The UI shows a SnackBar: "This time slot was just locked by another player."

3

15-minute hold timer

A Riverpod bookingTimerProvider starts a countdown from 15:00. On expiration, an alert dialog fires: "Your slot hold has expired." and the user is navigated back to Step 1. The lock is released via release_slot_lock(p_slot_id, p_user_id) RPC.

4

User completes booking

Step 4 inserts a bookings row with status = 'pending' and locked_until timestamp. The confirm_booking_payment(p_booking_id) RPC exists but is not yet called — payment integration is the blocking dependency for production.

5

User exits wizard early

On back-navigation or wizard abandonment, release_slot_lock(p_slot_id, p_user_id) is called to return the slot to available status immediately.

4 Version Control, Quality & CI/CD

GIT Branching Model

Feature branches from main. PR-based code review before merge. main is the production/stability branch. No develop or staging branch currently used.

ANALYSIS Static Analysis

dart analyze lib/ passes with 0 errors, 0 warnings. 16 info-level lints (pre-existing, primarily use_build_context_synchronously and unnecessary_underscores). Linting rules follow flutter_lints defaults.

ENV Configuration Management

Sensitive values stored in .env loaded at build time via flutter_dotenv. Keys: SUPABASE_URL, SUPABASE_ANON_KEY, STRIPE_PUBLISHABLE_KEY (pending). .env is gitignored.

PIPELINE CI/CD

No CI/CD pipeline configured. Builds are executed locally. Recommended: GitHub Actions with dart analyze, test runner, and flutter build on PR.
