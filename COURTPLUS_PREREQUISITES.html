1 Executive Summary

Court+ has completed its core engineering phase. Authentication (email/password, OTP, guest mode), slot-locking via Supabase RPCs, court discovery and filtering, profile management, and the 4-step booking wizard are all functional and verified with zero analyzer errors. The application architecture is stable and ready for the final production integration phase.

However, moving from a verified prototype to a commercially released product in the Saudi market requires explicit product definitions from agency leadership and access to operational credentials that cannot be mocked or stubbed. This document formally requests the clarifications, design handover, and account provisioning items that must be resolved before Court+ can be submitted to Apple App Store and Google Play Store.

2 Core Product & Architecture Clarifications

The following questions require written confirmation from Agency Leadership to finalise the social, discovery, and partner onboarding layers.

SOCIAL Social & Community Framework

1 What is the full vision for the social layer?
  • Is the social layer intended as a lightweight companion (rate players, share match results) or a full community platform (friend lists, feeds, leaderboards)?
  • Should we implement a friend request / accept system, or is social proximity based on shared court bookings and match participation?
  • Are there plans for player reputation or skill rating systems beyond the current static star rating on profiles?
2 How do players discover and connect with each other?
  • Search by name, username, or shared courts/coaches?
  • Suggested connections based on recent matches at the same venue?
  • QR code or shareable profile links for offline meetups?
3 What is the messaging architecture?
  • Strictly 1-on-1 direct messaging between connected players?
  • Group chats for match lobbies (captain + invited players)?
  • Is real-time presence (typing indicators, read receipts) required?
  • Should messaging use Supabase Realtime channels or a dedicated service (Sendbird, Stream Chat)?

MOMENTS Moments & Timeline Discovery

4 How are "Moments" viewed across the platform?
  • Private Friends Feed: Only posts from followed/connected players appear in a chronological timeline?
  • Global Public Feed: All user-uploaded moments visible to everyone, with algorithmic or recent-first sorting?
  • Venue-specific feed: Moments tagged to a particular court appear on that court's detail page?
5 What is the content moderation strategy?
  • Automated image/content filtering on upload?
  • User-flag/report mechanism with admin review queue?
  • Is there a need for a community guidelines document and in-app reporting flow?

OPERATIONS Partner Onboarding (Courts & Coaches)

6 What is the operational workflow for listing new courts and coaches?
  • Self-service Partner Portal: Courts and coaches submit their own profiles for admin approval, including photos, pricing, and availability schedules?
  • Manual provisioning: Agency/admin team ingests venue data via Supabase dashboard or seed scripts?
  • Hybrid model: Partner submits, admin reviews and publishes?
  • Who owns the photography and media assets for each venue?

3 Design & Frontend Codebase Handover

To ensure the Flutter implementation matches the approved product vision, the following handover items are required from the design and frontend teams.

A FIGMA Figma Master Design Schema
  • Full view/inspect access to the official Figma file covering all user flows: Onboarding, Auth, Home, Court Discovery, Booking Wizard, Profile, Social, Settings.
  • Complete component library (buttons, inputs, cards, bottom sheets, dialogs, status badges, skeleton states).
  • Design token specification: colour palette, typography scale (font sizes, weights, line heights), spacing grid, border radius values, and shadow/elevation definitions.
  • Empty state, loading state, and error state mockups for every primary screen.
  • RTL layout mockups for the Arabic localisation variant.
B CODE Frontend Reference Codebase
  • Source repository access (GitHub / GitLab) or a zip archive of the reference frontend project.
  • 2–3 fully implemented reference screens demonstrating the agreed routing, state management (Riverpod), API service layer, and design theme configuration.
  • Any existing widget tests or integration tests to validate that the reference implementation matches the Figma designs.
  • CI/CD configuration files if the reference project includes automated build and deployment pipelines.
